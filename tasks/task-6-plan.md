# Task 6 Plan: task-based execution and clear points

Source request: [task-6.md](task-6.md). Long features are split into parts, and the work is cut into units small enough that the user can clear the chat when a unit finishes. The request includes a ChatGPT proposal; this plan checks which parts of it apply.
State reviewed: specflow 0.9.0 (`70e8e46`, branch `task-6-token-efficiency`), the baseline in [docs/usage-findings.md](../docs/usage-findings.md), and the backlogs and specs of Wali App, madfit and HJI.

Status: **Draft. Part E decisions use the recommended defaults until the owner changes them.**

# Part A: The request in technical terms

1. **Decomposition.** A feature that is too large is split into slices, and each slice into tasks. The task is the smallest unit that can be run and checked on its own.
2. **Context isolation per unit.** Each builder run gets a self-contained execution contract for its tasks (objective, files, acceptance, rules, verification), so it does not have to rebuild the whole feature context.
3. **Clear points.** When a unit of work finishes, the main session (PM) saves state and tells the user it is safe to `/clear`. A fresh session resumes from disk in one or two turns.
4. **Model per task.** The model can be chosen per task, not only per feature.
5. **Measurable.** Savings are checked with `specflow usage` and the analysis scripts against the 2026-11-27 baseline.

# Part C: Cost model. Why "clear after every task" can cost more

- A fresh session starts at about 53k tokens (Claude Code's own prompt and tools). With the brief, handoff and flow skill, a restart costs about **62k plus about 3 turns to get oriented** (the `pmsim.mjs` model).
- The PM spends a median of **0-1 turns per finished subagent**. One builder batch adds only a few thousand tokens to the PM context.
- Simulated session budgets: 120k saves 16-21%, 100k saves 19-26%, 90k saves 21-27%. **The gain flattens below 100k** because each restart costs about 62k.

So clearing after every builder batch would pay the 62k restart cost many times for little gain. The useful cut points are **natural boundaries that also come late enough**: a gate approved, an item finished building (`verifying`), accepted, or done. These should count only once the context is past a soft threshold. F1 sets that threshold from real transcripts before any code is written.

On the builder side the effect is larger. Builders run a median of 20-31 turns, and every turn rereads the whole context. About 10k tokens of spec and plan that the card replaces are therefore paid about 25 times per run.

# Part D: Design

## D1. Clear points (PM session)
- New config: `session.clear_at`: `boundary` (default) or `budget` (0.9.0 behaviour only); `session.soft_budget` (default from F1, provisionally 75k).
- **Boundary events** on any item: a gate approved; stage moved to `verifying`, `accepted`, `released` or `done`; `rework start`. Builder batches are not boundaries.
- At the Stop hook, if the context is at or above `soft_budget` and a boundary event happened since the session started (or since the last clear-point message), the PM is asked to checkpoint and tell the user in one line: *"<id> <what finished>. State is saved. Safe to /clear, then say 'continue'."* This happens at most once per boundary. The hard budget (`context_budget`, 100k) works as before and takes priority.
- The handoff gets a **`Resume with:`** line containing the exact next command (for example `specflow dispatch F-012 --repo api --json`), so a fresh session goes from brief to handoff to dispatch without reading more.

## D2. Task card per builder batch
`specflow dispatch` for a builder writes `.specflow/cache/cards/<id>-<repo>.md` (overwritten on each dispatch) and adds `Card: <path>` to the prompt. The card is deterministic and at most about 120 lines or 8 KB:
- the header (item, slice parent, stage, lane, rework round, batch "T006-T010, 5 of 9 open");
- the full task lines of this batch;
- the acceptance text those tasks reference, taken from spec.md;
- the repo's row from plan.md's Repository Impact table;
- the branch, the test command and the rules ("only these tasks", "start from the files named", "targeted tests, quiet", "mark [X], checkpoint, return");
- "Read more only if the card is not enough: spec.md / plan.md / tasks.md (paths)".

The build skill changes from "read spec, plan, tasks" to "read the card; open spec or plan sections only for what the card lacks".

## D3. Model per task (optional)
The architect may tag a task `[model:haiku|sonnet|opus]`. Haiku is for mechanical tasks only: DTOs, config, renames, copy, simple tests. A batch stops at the first change of model, so every task in a batch shares one model. Under `model_policy: auto` the batch model is the tag, capped at the builder's configured model. Untagged tasks use today's item-level choice. `fixed` ignores the tags. `team.task_models: false` turns tags off.

## F3. Task cards
- New `lib/cards.mjs` exports `renderCard(ctx, f, repo, batch)` and `writeCard(...)`, returning the path relative to the root.
- **Reference extraction** (each referenced id once, in order of first appearance):

# Part G: Not doing (and why)
- **Epic level:** milestones already do this.
- **Parallel tasks in one repo:** branch conflicts and no token saving.
- **Clearing after every builder batch:** a 62k restart against a few thousand tokens of PM growth per batch (Part C). F1 shows the numbers.
- **An architect-written `task.md` per task:** costs architect (Opus) tokens and adds files; the CLI card gives the same contract for free.
- **A lower slice threshold now:** wait for 0.9.0 data (batches of 5 already shorten builder runs).
